Syslog listen ports

Which UDP/TCP port(s) the syslog listener binds. 514 is standard; add others (comma-separated) for devices that send elsewhere, e.g. 10514. Every port runs the same pipeline. The listener reads this at startup — changes here take effect only after you restart the listener process.

Restart required
Listen ports saved as . Restart the listener process for this to take effect. It's a separate process from this dashboard, so restarting it won't interrupt the console. For example:
sudo pkill -f listener.py
sudo python3 listener.py --db siem.db &

Monitor this host

Send the SIEM server's own logs into mini-SIEM, so it watches itself — logins, sudo, SSH, account changes, and the Linux audit trail. A SIEM that can't see its own host is blind to attacks against itself. Pick the sources below and paste the generated config on this server. Learn more

1 · rsyslog forwarding config

Save as /etc/rsyslog.d/60-minisiem.conf on this server, then sudo systemctl restart rsyslog.



    

      
2 · Bridge auditd → syslog

      
auditd doesn't go through rsyslog by default. Enable its syslog plugin so audit
        records reach the config above:

      
sudo apt-get install -y auditd audispd-plugins   # if not already installed
# enable the syslog plugin:
sudo sed -i 's/^active = no/active = yes/' /etc/audit/plugins.d/syslog.conf 2>/dev/null \
  || sudo sed -i 's/^active = no/active = yes/' /etc/audisp/plugins.d/syslog.conf
sudo systemctl restart auditd

      
Tip: to specifically watch a sensitive file or directory, add an audit rule, e.g.
        sudo auditctl -w /home/matt/siem123/mini_siem/siem.db -p wa -k siem_db.

    


    
Once running, this host's events appear in Log Search like any other source —
      searchable, correlated, and forwardable. They'll show the SIEM server's own hostname.

API log receiver

    
Accept logs over HTTP from products that can only send via an API (not raw syslog). Senders authenticate with an API key and POST to /api/ingest. Received logs run through the same pipeline as syslog — rules, threat-intel, field extraction, and forwarding all apply. Keys are shown once at creation and stored only as a hash; if you lose a key, delete it and make a new one.

      How to send logs
      

        
JSON (one object, a list, or {"logs":[…]}):

        
curl -X POST https://YOUR-SIEM/api/ingest \
  -H "X-API-Key: YOUR_KEY" \
  -H "Content-Type: application/json" \
  -d '{"severity":"warning","host":"appliance1","app":"imaging","message":"disk 90% full","disk":"/data"}'

        
Recognized keys: message/msg, severity/level, hostname/host, app/app_name. Any other scalar key (like disk) becomes a searchable field.

        
Raw syslog lines (Content-Type: text/plain, one per line) also work.

      

    

  


  

    
Ticket system connector

    
Automatically create a ticket in your ticketing system (Jira, ServiceNow, Zammad, osTicket, or any REST endpoint) for every alert at or above a severity threshold — including threat_intel_match alerts from IOC hits. Scheduled playbook reports with findings also raise alerts through the same path. This makes outbound HTTP calls from the SIEM to your ticket API.

Syslog forwarding

    

      Relay every received syslog message — the original raw text, exactly as it arrived —
      to one or more downstream receivers, in addition to storing it here. Config changes take effect
      within ~5 seconds without restarting the listener. Optional filters let a destination receive only
      a subset (by minimum severity and/or a regex over the raw message).
    

    

      Loop protection: destinations pointing at this listener's own address and port are automatically
      skipped by the listener. Still, be careful not to create indirect loops
      (A forwards to B, B forwards back to A) — each hop would re-receive and re-forward the same messages forever.
