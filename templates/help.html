Threat Intel & IOC feeds

Every incoming log is checked against the enabled indicators live at ingest. A match is recorded on the Threat Intel page and raises a threat_intel_match alert on the main dashboard (which auto-triages if the AI analyst is enabled).

Importing indicators (paste)

One indicator per line — either plain values, or CSV in the form value,type,threat. Lines starting with # are treated as comments and ignored. Duplicates are skipped. This works directly with copy-pastes from abuse.ch feeds (Feodo Tracker, URLhaus), Spamhaus DROP, or your own lists. The Feed name / source groups an import so you can manage or remove it as a set; Default severity and Default threat are applied to any indicator line that doesn't specify its own.

External feed URLs (auto-import)

Point mini-SIEM at a plain-text indicator list on the web (e.g. abuse.ch Feodo Tracker ipblocklist, URLhaus text feed, Spamhaus DROP) and it downloads and imports it — on demand or on a schedule. This makes outbound HTTP requests from the SIEM to the feed URL, so make sure that egress is allowed and the source is one you trust. The same line formats as pasting apply: one indicator per line, # comments, or CSV value,type,threat.

Feed authentication

Feeds that need an API key or token are supported through the same connector, using whichever scheme the provider's docs specify. The key is encrypted at rest and never shown again after saving.

  • Static header key — a fixed header carries the key (e.g. AlienVault OTX's X-OTX-API-Key, abuse.ch's Auth-Key, VirusTotal's x-apikey).
  • Authorization header (raw key) — the key goes in Authorization with no Bearer prefix (MISP's convention).
  • URL query parameter — the key is appended to the URL (Shodan-style, ?key=…).
  • HTTP Basic auth — key as username/password (IBM X-Force style).

A feed needing full OAuth2 client-credentials (e.g. CrowdStrike Falcon Intel) is better set up as an API poller connector under Setup, since that flow already exists there.

Log search

The message box uses the active database search engine shown directly below the filter bar. With the recommended text_search=auto, SQLite prefers FTS5 and PostgreSQL prefers indexed native FTS, with transparent LIKE/ILIKE fallback when an accelerator is unavailable. Source, Host, and Destination each search their base column plus any configured aliases (see below). Those three boxes accept comma-separated terms and now have their own AND / OR selector. The selector only controls terms inside that box: for example sophos,firewall with Source=OR matches either source. Different filter families still combine with AND, so Source=OR cannot bypass a Host, Destination, message, field, severity, or time filter. !term exclusions always remain mandatory. Fast identity matching is explicit: a full IP is exact, bare text is prefix, =value forces exact, value* is prefix, and *value* requests contains. IP-bearing fields also support subnet matching (192.168.1.0/24, or a dotted prefix such as 192.168.1).

Live refresh behavior

With Auto-refresh ON, Log Search polls every 5 seconds and Stats every 15 seconds. Alerts and the AI queue are not background-polled; use the top-level manual refresh or their explicit actions when you want fresh secondary-panel data. A background request is skipped while the same endpoint is still in flight, stale user-driven log/stat requests are cancelled, and hidden browser tabs pause live polling. In the normal recent-first view the 5-second poll sends the saved (received_at,id) cursor and asks only for chronologically newer rows. Unchanged rows are not transferred or rebuilt; only unseen rows are prepended, the visible window stays bounded at 200, and one delegated click handler serves the table instead of rebinding hundreds of row handlers. History clients can use the matching older cursor instead of large SQL OFFSETs.

Ingest / DB telemetry

The small telemetry line beside the refresh controls comes from the listener through the database, not from browser guesses. It shows recent ingest rate, receive and DB-writer queue depth, average DB micro-batch size, rolling commit p95, and drops. The listener owns one bounded database-writer queue and commits up to 100 prepared events or roughly 75 ms of work per transaction by default. Rules and IOC checks run only after that transaction has produced a durable log ID. Total-event, hourly severity, and source-last-seen rollups are updated in the same log transaction so the 15-second Stats request does not repeatedly aggregate the full log table.

Field filters & columns

Type field=value directly in the field box and press Enter, or expand any log row and click/drag its +. The field box has the same AND / OR selector; repeated names are preserved, so event_id=4624 OR event_id=4625 works as expected. Plain field=value is an indexed exact lookup; append * for prefix, or use field=*value* when a contains scan is really needed. field!=value is an exclusion and always remains mandatory. Message text and field filters are applied in the same query: a text search plus a field chip must satisfy both; field OR only changes how the positive field chips combine with each other. Click a field name to add it as a display column. Extracted fields are materialized at ingest into an indexed table, so filtering and sorting search your entire history, not just the visible page.

Cascade timeline

Cascade timeline uses the exact current Log Search filters and opens in a native HTML <dialog> above the dashboard, so it does not push the log table down or navigate away from Log Search. On desktop it uses about 90% of the viewport width and 85% of the height; on small screens it becomes full-screen. The first load takes the most recent 500 matching events and displays them chronologically. Refresh uses the timeline's own cursor and asks only for newer events. The logical timeline can grow while only cards near the visible horizontal viewport are mounted in the DOM (plus a small buffer), so opening or refreshing a long timeline does not permanently create thousands of card nodes. The client keeps the latest 5,000 loaded events per open timeline. Each card shows time in the form Jul 25 2011 23:15, a compact source-to-destination/host path, the first meaningful sentence or clause from Message, and an Event ID badge when one can be recognized. Close it with the top-right ×, Esc, or the shaded backdrop. Clicking a card closes the dialog and locates/highlights that event in the main log table; if the row is outside the normal 200-row page, the dashboard fetches that exact ID under the same filters and appends it before scrolling. The active search filters are not changed. Timeline is intentionally on-demand: opening the dialog loads it once, and its own Refresh button fetches only events after the saved timeline cursor. The 5-second Log Search auto-refresh does not rebuild the timeline in the background.

Search field aliases

Different sources use different field names for the same idea — Fortigate's src= and Sophos's endpoint_ip both identify "the source machine". Search field aliases (under Setup) let you declare, per concept, which raw field names also count as source, host, or destination. Then one Source search finds a machine regardless of which source reported it.

This resolves at query time, so edits apply to all historical data immediately — nothing needs reindexing. The correlation playbooks use the same aliases to group events by identity across sources, so search and correlation always agree on what "source" means.

How normalization works — the three layers

There are three distinct stages, each configured (or not) in a different place:

1. Field extraction (automatic)

Every event has all its fields pulled into a searchable table. JSON events (poller/API, e.g. Sophos): every top-level key becomes a field, and a nested source_info.ip is surfaced as endpoint_ip. key=value messages (e.g. Fortigate): every key=value token becomes a field. Custom regex patterns (saved from the expand panel) add extra fields. This layer is exhaustive and isn't configured per source — any field is searchable even if it isn't promoted to a column.

2. Built-in parsing (fixed, in code)

  • Fortigate: src= fills the Net-source column; dst= fills Destination. Note FTNTFGTlevel is Fortigate's own severity field — not the same as a mini-SIEM dashboard alert.
  • Windows / NXLog: EventID maps to severity via a built-in table (e.g. 4625 = failed logon, 1102 = audit log cleared).
  • All sources: timestamps normalized to ISO-8601; peer_ip records the true network sender.

3. Configured normalization (two editable tabs under Setup)

  • Source field mapping — per-source profiles that map a few chosen fields into the base columns (Host, Message, Severity, Timestamp). E.g. for Sophos, location → Host.
  • Search field aliases — cross-source concept aliases for search and correlation (above).

Correlation & playbooks

A dashboard alert is not a single log line — it's a correlation playbook firing when its pattern, grouping, threshold, and time window are all satisfied. Logs are the raw stream; alerts are the interesting patterns mini-SIEM extracts from it. One alert can reference many logs.

Playbooks group events by an identity (source, host, or user). For source/host/destination grouping, the engine resolves identity through the same Search field aliases as log search — so a poller source whose source_ip column holds a connector name (e.g. "sophos") still correlates by the real per-endpoint IP, not the shared connector name.

Performance, archive & health

The status strip above Log Search shows current ingest queue depth, DB-writer queue depth, micro-batch size, commit p95, query latency, and an overall HEALTHY / DEGRADED / OVERLOADED state. The state is based on current queue pressure and recent interval drops/failures; an old historical drop counter does not leave the system permanently overloaded.

Query telemetry stores only coarse classes and timings — never your search text, field values, IP filters, usernames, or other query content. The default slow-query threshold is 250 ms.

Archive & lossless deduplication

mini-SIEM does not age-delete evidence. Archive is OFF by default. When enabled, old hot rows are copied into immutable, checksummed SQLite archive segments. mode=copy keeps both copies; mode=move evicts the hot copy only after the archive segment is committed, compacted, checksummed, cataloged, reopened, and verified.

Archive deduplication is exact and evidence-preserving. Every occurrence keeps its original log ID and receive time, while byte-equivalent event payloads and extracted fields are stored once per segment. Similar-but-not-identical events are never collapsed, because repetition itself can be security evidence. Normal Log Search, field filters, Timeline, and row expansion include sealed archive evidence; an unreadable expected segment returns an explicit archive error instead of a false empty result.

SQLite maintenance never runs a live full VACUUM. It uses bounded PASSIVE WAL checkpoints, incremental free-page reclamation only with auto_vacuum=INCREMENTAL, PRAGMA optimize, and a rate-limited quick_check. Query telemetry remains observation-only: telemetry failure cannot alter the real Log Search WHERE clause or suppress rows.

IOC architecture

The existing IOC matcher remains available, but this evidence-lifecycle phase does not make a new IOC architecture decision. Whether IOC matching stays embedded or moves to a separate enrichment service is intentionally left open.

Monitor this host

A SIEM that can't see its own host is blind to attacks against itself. This section (Setup → Monitor this host) generates config to forward the SIEM server's own logs into mini-SIEM, so its logins, sudo, SSH, and audit trail are searchable and correlated alongside everything else.

Two kinds of "audit log" on Linux

  • Authentication (auth.log) — handled by rsyslog/journald: logins, sudo, su, sshd. The everyday "who logged in / who ran sudo" events. Forwarding this needs only the rsyslog config.
  • Linux audit trail (auditd) — the compliance-grade audit log (/var/log/audit/audit.log): syscall-level records, file-access watches, account and policy changes. auditd does not flow through rsyslog by default, so it needs a one-time bridge (the audisp syslog plugin) before its records can be forwarded.

How it works

The generated rsyslog config sends the selected facilities to the listener's address/port using standard syslog (@ for UDP, @@ for TCP). When the listener runs on this same box, 127.0.0.1 keeps the traffic on-host. Once rsyslog is restarted (and auditd bridged, if you chose the audit trail), the host's events appear in Log Search under the server's own hostname — searchable, correlated, and forwardable like any other source.

Watching specific files

To audit access to a sensitive file or directory, add an auditd watch rule, e.g. sudo auditctl -w /path/to/siem.db -p wa -k siem_db (-p wa = writes and attribute changes; -k tags the events with a searchable key). Make it persistent by adding the same rule to /etc/audit/rules.d/.
