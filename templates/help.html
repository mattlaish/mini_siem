Threat Intel & IOC feeds

Every incoming log is checked against the enabled indicators live at ingest. A match is recorded on the Threat Intel page and raises a threat_intel_match alert on the main dashboard (which auto-triages if the AI analyst is enabled).

Importing indicators (paste)

One indicator per line — either plain values, or CSV in the form value,type,threat. Lines starting with # are treated as comments and ignored. Duplicates are skipped. This works directly with copy-pastes from abuse.ch feeds (Feodo Tracker, URLhaus), Spamhaus DROP, or your own lists. The Feed name / source groups an import so you can manage or remove it as a set; Default severity and Default threat are applied to any indicator line that doesn't specify its own.

External feed URLs (auto-import)

Point mini-SIEM at a plain-text indicator list on the web (e.g. abuse.ch Feodo Tracker ipblocklist, URLhaus text feed, Spamhaus DROP) and it downloads and imports it — on demand or on a schedule. This makes outbound HTTP requests from the SIEM to the feed URL, so make sure that egress is allowed and the source is one you trust. The same line formats as pasting apply: one indicator per line, # comments, or CSV value,type,threat.

Feed authentication

Feeds that need an API key or token are supported through the same connector, using whichever scheme the provider's docs specify. The key is encrypted at rest and never shown again after saving.

  • Static header key — a fixed header carries the key (e.g. AlienVault OTX's X-OTX-API-Key, abuse.ch's Auth-Key, VirusTotal's x-apikey).
  • Authorization header (raw key) — the key goes in Authorization with no Bearer prefix (MISP's convention).
  • URL query parameter — the key is appended to the URL (Shodan-style, ?key=…).
  • HTTP Basic auth — key as username/password (IBM X-Force style).

A feed needing full OAuth2 client-credentials (e.g. CrowdStrike Falcon Intel) is better set up as an API poller connector under Setup, since that flow already exists there.

Log search

The message box does a full-text search of the log message (prefix-matching on word tokens, via FTS). Source, Host, and Destination each search their base column plus any configured aliases (see below). All boxes support !term to exclude, comma-separated terms, and — for the IP-bearing fields — subnet matching (192.168.1.0/24, or a dotted prefix like 192.168.1).

Field filters & columns

Click any log row to expand it and see every extracted field with its exact name and value. Click a field name to add it as a column; click the + (or drag it) to add it as a filter condition. With two or more filter conditions, an AND / OR toggle appears to control how they combine. Extracted fields are materialized at ingest into an indexed table, so filtering and sorting search your entire history, not just the visible page.

Search field aliases

Different sources use different field names for the same idea — Fortigate's src= and Sophos's endpoint_ip both identify "the source machine". Search field aliases (under Setup) let you declare, per concept, which raw field names also count as source, host, or destination. Then one Source search finds a machine regardless of which source reported it.

This resolves at query time, so edits apply to all historical data immediately — nothing needs reindexing. The correlation playbooks use the same aliases to group events by identity across sources, so search and correlation always agree on what "source" means.

How normalization works — the three layers

There are three distinct stages, each configured (or not) in a different place:

1. Field extraction (automatic)

Every event has all its fields pulled into a searchable table. JSON events (poller/API, e.g. Sophos): every top-level key becomes a field, and a nested source_info.ip is surfaced as endpoint_ip. key=value messages (e.g. Fortigate): every key=value token becomes a field. Custom regex patterns (saved from the expand panel) add extra fields. This layer is exhaustive and isn't configured per source — any field is searchable even if it isn't promoted to a column.

2. Built-in parsing (fixed, in code)

  • Fortigate: src= fills the Net-source column; dst= fills Destination. Note FTNTFGTlevel is Fortigate's own severity field — not the same as a mini-SIEM dashboard alert.
  • Windows / NXLog: EventID maps to severity via a built-in table (e.g. 4625 = failed logon, 1102 = audit log cleared).
  • All sources: timestamps normalized to ISO-8601; peer_ip records the true network sender.

3. Configured normalization (two editable tabs under Setup)

  • Source field mapping — per-source profiles that map a few chosen fields into the base columns (Host, Message, Severity, Timestamp). E.g. for Sophos, location → Host.
  • Search field aliases — cross-source concept aliases for search and correlation (above).

Correlation & playbooks

A dashboard alert is not a single log line — it's a correlation playbook firing when its pattern, grouping, threshold, and time window are all satisfied. Logs are the raw stream; alerts are the interesting patterns mini-SIEM extracts from it. One alert can reference many logs.

Playbooks group events by an identity (source, host, or user). For source/host/destination grouping, the engine resolves identity through the same Search field aliases as log search — so a poller source whose source_ip column holds a connector name (e.g. "sophos") still correlates by the real per-endpoint IP, not the shared connector name.

Monitor this host

A SIEM that can't see its own host is blind to attacks against itself. This section (Setup → Monitor this host) generates config to forward the SIEM server's own logs into mini-SIEM, so its logins, sudo, SSH, and audit trail are searchable and correlated alongside everything else.

Two kinds of "audit log" on Linux

  • Authentication (auth.log) — handled by rsyslog/journald: logins, sudo, su, sshd. The everyday "who logged in / who ran sudo" events. Forwarding this needs only the rsyslog config.
  • Linux audit trail (auditd) — the compliance-grade audit log (/var/log/audit/audit.log): syscall-level records, file-access watches, account and policy changes. auditd does not flow through rsyslog by default, so it needs a one-time bridge (the audisp syslog plugin) before its records can be forwarded.

How it works

The generated rsyslog config sends the selected facilities to the listener's address/port using standard syslog (@ for UDP, @@ for TCP). When the listener runs on this same box, 127.0.0.1 keeps the traffic on-host. Once rsyslog is restarted (and auditd bridged, if you chose the audit trail), the host's events appear in Log Search under the server's own hostname — searchable, correlated, and forwardable like any other source.

Watching specific files

To audit access to a sensitive file or directory, add an auditd watch rule, e.g. sudo auditctl -w /path/to/siem.db -p wa -k siem_db (-p wa = writes and attribute changes; -k tags the events with a searchable key). Make it persistent by adding the same rule to /etc/audit/rules.d/.
